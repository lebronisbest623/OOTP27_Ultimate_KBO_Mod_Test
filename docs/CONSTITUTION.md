# OOTP27 KBO Launcher 헌법

이 문서는 코드베이스를 지배하는 불변의 원칙들을 규정한다.  
ARCHITECTURE.md가 현재 구조를 기술한다면, 이 헌법은 그 구조가 왜 그래야 하는지를 규정한다.  
새 코드는 이 원칙들을 따라야 한다. 이 원칙들에 반하는 코드는 병합되어선 안 된다.

---

## 제1장 — 존재 이유

이 프로젝트는 OOTP27이 네이티브로 지원하지 않는 KBO 규칙을 구현하기 위해 존재한다.  
게임의 소스코드 없이 실행 중인 바이너리에 훅을 걸어 동작한다.

이 제약은 아키텍처의 모든 선택을 설명한다.  
단일 번역 단위 빌드, include 순서 API, 하드코딩된 오프셋은 이 제약에서 출발한 역사적 결과다.  
그러나 역사적 결과는 영구 원칙이 아니다. 제약을 우회하지 말되, 제약을 더 작고 검증 가능한 경계로 나누는 이주는 허용한다.

---

## 제2장 — 두 레이어

이 프로젝트는 두 레이어로 구성된다. 레이어를 혼용하지 않는다.

### 제1조 — 관리 레이어 (C#)

`Program.cs`는 관리 레이어의 유일한 진입점이다.  
관리 레이어의 책임:

- OOTP 실행 파일 위치 확인
- 런타임 데이터 파일 준비 (`%LOCALAPPDATA%\OOTP-KBO\`)
- 게임 프로세스 시작 또는 기존 프로세스에 attach
- 네이티브 패치 DLL 주입

관리 레이어는 KBO 규칙을 직접 구현하지 않는다.  
관리 레이어는 네이티브 레이어가 읽을 데이터를 준비할 뿐이다.

`LauncherApp.Run`은 관리 레이어의 조립 셸이다. 셸의 책임:

- 옵션 파싱 실패와 도움말 처리
- 실행 컨텍스트 조립
- 준비/검증/attach/launch 플로우로 위임

`LauncherApp.Run`에 프로세스 탐색, 빌드 판정, 런타임 데이터 준비, DLL 인젝션 세부 절차를 직접 누적하지 않는다.  
관리 레이어도 네이티브 레이어와 같은 원칙을 따른다 — 진입점은 얇고, 책임 단위는 이름 있는 모듈로 분리한다.

지원 OOTP 빌드 목록은 `config/ootp-supported-builds.json`만 원천으로 삼는다.  
C# 런처와 네이티브 DLL은 이 manifest에서 생성된 소스만 사용한다.  
지원 빌드를 추가하거나 제거할 때는 manifest를 수정하고 생성 스크립트를 실행한 뒤, 관리 테스트가 manifest/C#/C 목록 일치를 검증해야 한다.

### 제2조 — 네이티브 레이어 (C)

`native/KBOFix.c`는 현재 네이티브 레이어의 주 진입 번역 단위다.  
KBO 규칙 에뮬레이션은 전적으로 네이티브 레이어에 속한다.

`native/KBOFix.c`는 쉘이다. 쉘의 내용:

- OOTP ABI 오프셋 상수
- ABI 타입 정의 (typedef)
- 훅 함수 프로토타입
- 공유 저수준 헬퍼
- 현재 단일 TU 호환에 필요한 `.inc` include 순서

도메인 로직은 `KBOFix.c`에 작성하지 않는다. 도메인 상태는 소유 서브시스템의 state 모듈에 속한다.  
새 네이티브 번역 단위가 생기더라도 `KBOFix.c`는 진입점, ABI 경계, 패치 설치 순서의 조립 책임만 가진다.

---

## 제3장 — 네이티브 컴파일 경계와 include 규칙

### 제3조 — include 순서는 현재 호환 API다

단일 번역 단위 빌드에서 `.inc` 파일의 include 순서는 선언 순서다.  
나중에 include된 파일은 먼저 include된 파일의 심볼을 사용할 수 있다.  
반대 방향 참조는 전방 선언으로만 해결한다.

파일을 재배치할 때는 반드시 선언 순서가 보존되는지 확인한다.  
컴파일이 되었다고 해서 순서가 올바른 것은 아니다 — 의존 방향이 역전되었을 수 있다.

이 규칙은 현재 구조를 안전하게 유지하기 위한 호환 규칙이지, 새로운 코드가 영구히 단일 TU에 머물러야 한다는 명령이 아니다.

### 제3-1조 — 다중 번역 단위 이주를 허용한다

네이티브 코드는 기능 단위로 `.c` / `.h` 번역 단위로 이주할 수 있다.  
이주는 다음 조건을 만족해야 한다:

1. 새 번역 단위는 소유 서브시스템과 책임이 명확해야 한다.
2. 외부로 노출되는 심볼은 헤더에 선언하고, 내부 구현은 `static`으로 숨긴다.
3. OOTP ABI 오프셋, 패치 설치 진입점, 런타임 시작 순서는 중앙 조립 레이어에서 추적 가능해야 한다.
4. 단일 TU에서 다중 TU로 옮기는 변경은 한 번에 한 서브시스템 또는 한 책임 단위로 제한한다.
5. 각 단계는 native 빌드와 관리 런처 빌드로 검증한다.

다중 TU 이주는 성능 최적화만을 위한 작업이 아니다. 모듈 격리, forward declaration 감소, 변경 범위 축소를 위한 구조 개선이다.

이미 기준선에 여러 서브시스템이 섞여 들어온 마이그레이션 부채가 발견되면, 그 사실을 `ARCHITECTURE.md`의 마이그레이션 계획에 책임 단위별로 기록한다.  
그 기록은 새 예외가 아니다. 이후 코드는 기록된 책임 단위를 하나씩 닫아야 하며, 여러 책임 단위를 한 커밋에 함께 닫지 않는다.

### 제4조 — 순환 의존을 해결하는 방법

두 모듈이 서로를 필요로 하면, 다음 순서로 해결한다:

1. `foreign_waiver_decls.inc` 또는 `military_service_decls.inc`에 좁은 전방 선언을 추가한다.
2. 공통 부분을 작은 공유 헬퍼 모듈로 분리한다.
3. 다중 TU로 아직 옮기지 않은 코드에서는 **두 모듈을 합치는 것은 최후의 수단이며, 두 모듈의 책임을 진지하게 재검토한 이후에만 허용된다.**

### 제5조 — 루트 파일은 얇게 유지한다

`native/src/` 직접 하위 `.inc` 파일이 include 순서와 작은 상수 이상으로 커지면,  
해당 내용을 서브폴더로 이동하고 루트 파일은 안정적인 진입점으로만 남긴다.

## 제4장 — 모듈 계층

### 제6조 — 계층 구조

모듈은 다음 계층 중 하나에 속한다. 역방향 호출은 금지된다.

```
┌─────────────────────────────────┐
│  훅 래퍼 / 패치 인스톨러         │  ← OOTP 바이너리 패치 지점
├─────────────────────────────────┤
│  스캐너 / 쓰레드 루프            │  ← 타이밍 소유
├─────────────────────────────────┤
│  AI / 커맨드 실행                │  ← 결정 실행
├─────────────────────────────────┤
│  정책 / 이벤트 창                │  ← 결정 허가
├─────────────────────────────────┤
│  도메인 로직 (권리, 제한, 쿼터)   │  ← 게임플레이 상태 변경
├─────────────────────────────────┤
│  I/O / 영속성                    │  ← CSV, 플래그 파일
├─────────────────────────────────┤
│  상태 / 선언 / 상수              │  ← 구조체, 전역 변수
└─────────────────────────────────┘
```

### 제7조 — 각 계층의 규칙

**훅 래퍼**: OOTP 내부 함수 호출을 가로채고 도메인 정책에 위임한다. 훅 래퍼 자체에 정책 로직을 작성하지 않는다.

**스캐너/쓰레드**: 폴링 타이밍을 소유한다. 도메인 도메인 동작을 직접 구현하지 않고 도메인 모듈을 호출한다.

**AI/커맨드 실행**: 무엇을 할지 결정한다. 권리 테이블, 이벤트 창, 서명 가능성 훅을 직접 소유하지 않는다.

**정책/이벤트 창**: 결정이 언제 합법적인지 판단한다. 어떤 선수를 보류할지 선택하지 않는다.

**도메인 로직**: 게임플레이 상태를 변경한다. I/O 모듈이 아니라 상태 모듈을 통해 상태를 읽고 쓴다.

**I/O/영속성**: CSV와 플래그 파일만 읽고 쓴다. 게임플레이 상태를 직접 변경하지 않는다.

**상태/선언**: 구조체, 전역 변수, 상수만 정의한다. 함수 구현은 상태 모듈에 없다.

---

## 제5장 — 감사 모듈

### 제8조 — 감사 모듈은 관찰만 한다

`roster_audit`, `nation_id_scan`, `foreign_asian_quota_probe_log`와 같은 진단 모듈은  
게임플레이 상태를 절대 변경하지 않는다.

이 규칙은 예외가 없다. 진단 코드에서 상태를 변경하는 부수효과는 발견 즉시 제거한다.

---

## 제6장 — UI 모듈

### 제9조 — UI는 명령하지 않고 요청한다

`hotkey_window`와 F2 허브 UI는 게임플레이 상태를 직접 변경하지 않는다.  
UI 모듈이 할 수 있는 것:

- 선수 선택
- 커맨드 파일에 커맨드 기록
- 도메인 API를 통한 조회

UI 모듈이 할 수 없는 것:

- 권리 테이블 직접 변경
- 시드 테이블 직접 변경
- 플레이어/팀 메모리 직접 변경

---

## 제7장 — 파일 조직

### 제10조 — 레포지터리 루트 위생

레포지터리 루트는 프로젝트 진입점만 포함한다:

- `.sln` 솔루션 파일
- 런처 프로젝트 파일 및 소스
- 시작 스크립트 (`.bat`)

도메인 데이터는 루트에 두지 않는다.

### 제11조 — 번들 시드 파일 위치

번들 시드 CSV는 `data/seeds/` 아래에 위치한다.  
런타임에 `Program.cs`가 `%LOCALAPPDATA%\OOTP-KBO\`로 복사한다.  
새 시드 파일도 이 패턴을 따른다.

### 제12조 — 런타임 데이터 경로 규칙

세이브 스코프 파일이 먼저 읽힌다. 없으면 `%LOCALAPPDATA%\OOTP-KBO\`로 폴백한다.  
해석된 캐시, 감사 CSV, 출력 파일은 세이브 스코프 또는 모듈 소유 경로에 쓴다.  
글로벌 경로는 읽기 폴백 전용이다 — 출력 목적지로 쓰지 않는다.

### 제13조 — CSV 파일 소유권

각 CSV 파일은 정확히 하나의 모듈이 소유한다.  
파일 경로를 정의한 모듈이 그 파일의 읽기/쓰기를 소유한다.  
경로 소유권은 해당 모듈의 `_paths.inc` 파일에 주석으로 명시한다.  
다른 모듈이 같은 파일에 직접 접근하지 않는다 — 소유 모듈의 API를 사용한다.

---

## 제8장 — 서브시스템 어셈블러 패턴

### 제14조 — 어셈블러 파일의 정의

어셈블러 파일은 현재 단일 TU 호환 레이어에서 서브폴더의 상세 파일들을 dependency 순서대로 include하는 쉘이다.  
어셈블러 파일이 포함할 수 있는 것:

- `#include` 지시문
- `#define` 컴파일 타임 상수
- 한두 줄의 브리지 코드 (불가피한 경우에 한해)

어셈블러 파일에 도메인 로직을 작성하지 않는다.  
서브시스템이 다중 TU로 이주되면 어셈블러 파일은 호환 wrapper로 남기거나 제거할 수 있다. 이때 외부 진입점과 패치 설치 순서는 명시적인 헤더/소스 경계로 옮긴다.

### 제15조 — 서브폴더 깊이

중첩은 도메인이 독립적인 라이프사이클을 가질 때만 허용된다.  
현재 최대 깊이: `src/서브시스템/서브서브시스템/`  
예: `military_service/seed/`

더 깊은 중첩은 설계가 잘못되었다는 신호다 — 먼저 책임을 재검토한다.

---

## 제9장 — 상태 관리

### 제16조 — 보류권의 기원

OOTP 메모리에 `active_team_id`가 있다고 해서 보류권이 행사된 것이 아니다.  
보류권은 오직 다음 중 하나로만 생성된다:

1. 이벤트 창이 열려 있는 동안 보류 결정이 내려진 경우
2. `foreign_waiver_rights.csv`에서 로드된 경우

이 불변 조건을 어기는 코드는 즉시 제거한다.

### 제17조 — 도메인 상태와 OOTP 메모리의 분리

도메인 상태(권리 테이블, 군복무 대출 레지스트리, 부상 슬롯 테이블)는  
OOTP 메모리에서 파생되는 것이 아니라 독립적으로 관리된다.  
OOTP 메모리 동기화는 상태를 적용하는 마지막 단계이지, 상태의 원천이 아니다.

### 제18조 — 잠금 규칙

공유 테이블에 접근하는 스캐너 쓰레드와 훅 컨텍스트는 모듈이 정의한 잠금을 사용한다.  
잠금은 가능한 좁은 범위에서 유지한다.  
잠금을 보유한 상태에서 다른 잠금을 획득하지 않는다.

---

## 제10장 — 쓰레드 소유권

### 제19조 — 쓰레드 시작 함수의 소유

쓰레드 시작 함수는 명시적이어야 하고, 해당 루프를 소유한 모듈에 위치한다.  
`foreign_waiver_scanner.inc`가 외국인 보류권 스캐너 쓰레드를 시작한다.  
`custom_event_monitor.inc`가 커스텀 이벤트 모니터 쓰레드를 시작한다.  
`military_days_tick.inc`가 군복무 틱 쓰레드를 시작한다.

한 모듈의 쓰레드를 다른 모듈이 시작하지 않는다.

---

## 제11장 — 커스텀 이벤트

### 제20조 — 스캐너와 도메인의 분리

`custom_event_scan.inc`는 이벤트 매니저 순회, 만료 확인, 마커 기록을 소유한다.  
도메인 동작은 `custom_event_dispatch.inc`에 위임한다.  
스캐너에 도메인 로직을 직접 작성하지 않는다.

### 제21조 — 새 커스텀 이벤트 추가 방법

새 커스텀 이벤트는 다음 두 가지만 추가한다:

1. `custom_event_names.inc`에 이름 매처
2. `custom_event_dispatch.inc`에 도메인 핸들러 호출

`scan_kbo_custom_events_once`에 인라인 로직을 추가하지 않는다.

### 제22조 — 이벤트 핸들러 멱등성

`custom_event_markers.inc`의 마커가 멱등성의 경계다.  
이벤트 핸들러는 두 번 호출되어도 안전해야 한다.  
핸들러 내부에서 "이미 처리됨" 여부를 다시 검사하지 않는다 — 마커가 보장한다.

---

## 제12장 — 훅 래퍼

### 제23조 — 래퍼 이름 안정성

`patch_installers.inc`에 등록된 훅 래퍼 이름은 패치 설치 코드를 동시에 수정하지 않는 한 변경하지 않는다.  
래퍼 이름은 외부 API다.

### 제24조 — 래퍼의 두께

훅 래퍼는 얇아야 한다. 래퍼가 할 수 있는 것:

- 인자를 도메인 함수에 전달
- 반환값을 OOTP ABI 형식으로 변환
- 기존 동작을 호출할지 우회할지 선택

래퍼에 직접 정책 로직을 작성하지 않는다. 정책은 도메인 모듈에 있다.

## 제14장 — 금지 사항

다음은 무조건 금지된다. 이 금지 사항들은 과거의 실패에서 비롯되었다.

**금지 1**: 어셈블러 파일에 도메인 로직 작성  
**금지 2**: 감사/진단 모듈에서 게임플레이 상태 변경  
**금지 3**: UI 모듈에서 권리 테이블 직접 변경  
**금지 4**: OOTP `active_team_id`에서 보류권 존재를 추론  
**금지 5**: 스캐너 루프에 도메인 로직 인라인 작성  
**금지 6**: CSV 파일을 소유 모듈 외부에서 직접 열기  
**금지 7**: 글로벌 데이터 경로를 출력 목적지로 사용  
**금지 8**: 잠금 보유 중 다른 잠금 획득  
**금지 9**: 패치 설치 코드 수정 없이 훅 래퍼 이름 변경  
**금지 10**: 두 모듈의 순환 의존을 두 파일 합치기로 해결  
**금지 11**: 새 코드를 단일 TU에 숨겨 모듈 경계를 우회

### 제27조 — 모든 네이티브 변경 후 빌드 확인

```powershell
powershell -ExecutionPolicy Bypass -File native\build.ps1
dotnet build .\OOTP27-KBO-Launcher.sln
```

### 제28조 — 마이그레이션 검증

모듈을 분리하거나 파일을 이동할 때마다 빌드로 검증한다.  
한 번에 전체 마이그레이션을 하지 않는다 — 빌드 가능한 단계로 나눈다.  
각 단계는 독립적으로 커밋 가능해야 한다.

## 부칙 — 이 헌법의 개정

이 헌법은 다음 두 조건을 모두 충족할 때만 개정된다:

1. 기존 원칙이 실제로 나쁜 결과를 낳았음이 증명된 경우
2. 새 원칙이 기존 코드베이스에서 이미 동작한다고 검증된 경우

아직 구현되지 않은 이상을 헌법에 추가하지 않는다.  
단, 현재 구조의 검증된 비용을 줄이기 위한 이주 원칙은 헌법에 추가할 수 있다. 이 경우 헌법은 최종 형태를 강제하지 않고, 안전하게 이동할 수 있는 방향과 금지선을 규정한다.
